SillyTavern 入门：角色、记忆与预设

上下文、记忆、预设，以及类脑的资源生态。

2026 年 11 月 3 日·约 12 分钟·Markdown 原文

SillyTavern，大家常说的“酒馆”，是一套面向聊天和角色扮演的应用，提供模型连接、提示词组织、会话管理和扩展机制。它本身不提供模型，导入角色卡也不会改变模型权重。人物、故事和生成规则由角色卡、世界书与预设共同组织。

我自己的酒馆目前通过 GPTClub 中转接入模型。酒馆搭好后，按站内说明选好接口类型，填入接口地址和 API Key，再选择可用模型，就能先用简单角色卡开始聊天，不需要自行部署模型。预设和记忆功能可以在玩起来之后再逐步调整。

它值得介绍的地方，是把很多原本要自己写代码的上下文管理工作，做成了可以配置、导入和复用的功能。

01

一轮对话，酒馆在做什么

在常见的 Chat Completions 用法里，模型主要依据这一次请求中的内容生成回复。上一轮聊过什么，要由应用再次提供，不能把 API 当作已经记住全部对话的有状态对象。

酒馆的一轮生成可以概括为下面的流程。这里表示职责，不表示固定的消息排列顺序：

角色卡 / 用户人设 / 世界书 / 预设规则
最近对话 / 作者注释 / 已启用的记忆与工具
                    ↓
按位置、消息角色、触发条件和 token 预算组织请求
                    ↓
模型 API → 回复 / 工具调用 → 显示、存档与扩展处理

同样一句“我推门进去”，前面放了什么设定、过去发生过什么、要求怎样叙述，都会影响结果。你在酒馆里调的很多开关，实际是在改变这次请求的输入与处理方式。

因此，“本地部署酒馆”指运行这套应用；模型可以在本地，也可以在远端。使用远端 API 时，本轮组装出的上下文仍会发送给所选服务。更换模型通常可以保留角色与会话，但文风、指令遵循和格式兼容性需要重新观察。

02

它和带记忆的角色扮演 agent 有什么区别

“带记忆”和“agent”是两个维度。一个角色聊天应用可以只有“读取记忆 → 生成回复 → 更新记忆”这条链路；更强调自主性的 agent，还会围绕目标决定下一步、执行动作、观察结果，再继续行动。

比如，同样扮演侦探：“记得昨天见过证人”是记忆能力；“发现线索不足，主动查询档案并根据结果调整调查”涉及行动与控制流程。仅仅保存聊天历史，或调过一次工具，都不足以描述后者。

酒馆主要把角色扮演需要的上下文和交互控制暴露给使用者：你决定人物、背景、文风、模型，以及剧情从哪里分支。它也支持工具调用和扩展，可以承载更自动化的流程，所以两类系统没有绝对边界。

选择的重点是你想把精力放在哪里：自行实现 agent，可以完整控制状态、检索和执行循环；使用酒馆，可以先利用现成的编辑器、会话操作和社区资源，再在需要的地方加脚本。两条路线都能做角色扮演，也都要处理上下文与状态的一致性。

03

记忆不是一个开关

先区分两件事：聊天文件保存了多少内容，以及模型这一轮实际看到了多少内容。前者可以很长，后者受模型、接口和配置的上下文预算限制。

举个简化例子：如果接口共享一个 32K token 的输入输出窗口，预留 4K 回复，角色、预设和背景占 6K，留给原始聊天的大约就是 22K，还要考虑消息包装等开销。把酒馆里的上限调大，不会改变服务端的真实限制。

长线剧情通常要组合几种手段：

方式 主要作用 容易出的问题
最近聊天 保留刚发生的对话和细节 越早的内容越容易被挤出窗口
剧情摘要 将旧情节压缩成较短文本 细节丢失、总结错误、反复更新后偏移
向量检索 按语义相关性找回旧片段 可能漏检，也可能找到相似但不适用的内容
结构化状态 保存地点、物品、任务阶段、关系等字段 提取错误、更新遗漏、状态与正文不同步

窄屏下可横向滑动表格，查看完整内容。

这些机制解决的问题不同。摘要适合保留事件脉络，检索适合补回分散的信息，变量或数据库适合维护明确的游戏状态。检索出来的内容还要进入请求，模型才能利用它；状态表有 schema，也只能约束结构，不能证明里面的事实正确。

酒馆有摘要、向量检索等扩展，社区还提供变量与数据库方案。它们需要实际启用、配置和验证。看到界面上有一张状态表，并不代表模型这一轮读到了它，也不代表每次回复后都正确更新了。

04

几个基础功能，分别负责什么

角色卡与用户人设：定义对话双方

角色卡通常包含人物描述、性格、场景、开场白和示例对话；复杂卡还可能携带世界书、正则与脚本。它可以定义一个人物，也可以定义一组人物和一套冒险场景。

常见的 PNG 角色卡，本质上是在图片元数据里携带 JSON。酒馆读取其中的设定，不是让模型看图猜人物。因此应下载原始卡文件，截图或转换图片格式可能丢掉卡数据。用户人设则定义“我是谁”，例如身份、背景和与对方的关系，避免每次重新交代。

世界书：按条件装入背景

World Info / Lorebook 可以把城市、组织、人物关系拆成条目。比如对话提到“灰港”，便激活当地势力和规则；核心世界观也可以设为常驻。实际激活还受扫描范围、配置、优先级与预算等影响。

可以把它理解为带触发规则的背景注入系统，而不能直接等同向量数据库。普通关键词条目也能工作；不触发的条目通常不进入请求，进入之后仍占上下文。它也不会天然把每轮新剧情自动写回设定。

作者注释：短期导演指令

Author’s Note 适合放“当前是审讯场景，先保持嫌疑人的戒心”“不要提前揭晓凶手”这样的短指令，可以按位置、深度和间隔插入。人物长期性格放角色卡，场景临时要求放作者注释，通常更容易管理。

它与角色卡作者留给读者的使用说明不是同一个字段，也不是自动记忆功能。

重生成、编辑与分支：控制会话走向

一次回复不合适，可以重生成并切换不同版本；某句话写错，可以编辑；想试另一种选择，可以从已有节点建立分支。它们改变的是会话内容与后续上下文，让你能像调试一段交互流程一样调整故事。

如果某个扩展把变量或数据库另存，还要确认这些状态是否随分支同步。聊天分支不能自动保证所有第三方状态也完成了快照和回滚。

正则与扩展：处理文本，补上交互能力

正则常用于清理标签、折叠内容、调整显示，也可能作用于输入或发给模型的文本，要区分“仅显示”和“仅提示词”等范围。界面里隐藏了某段文字，不一定代表它没有送给模型。

酒馆助手、变量框架等扩展则能支持脚本、交互面板和状态更新。看到一张带背包、地图或任务面板的卡，可以把它视为附带运行依赖的小应用，按作者清单装配会更稳妥。

05

我装的两套预设

预设主要组织提示词和生成设置：各段指令放在哪里、是否启用、输出多长、采用什么叙事方式。角色卡偏向“谁在什么场景里”，预设偏向“怎样生成”，但两者可能写入重叠甚至相互冲突的规则。

小猫之神 Reborn 2.4.2

我这套用于 Gemini。作者主打角色的“活人感”，包含叙事相关指令，以及行动选项、小总结等可选模块，配套功能需要结合酒馆助手等依赖使用。它不是一个单纯的温度参数组合，而是一整套生成与展示约定。

这类预设要把提示词、正则、脚本和工具绑定当作一个整体看。我之前排查过一种空回复：生成指令仍要求调用某个工具，但请求里已经没有该工具。只关掉界面上的一个模块，不一定就清除了所有关联配置。

夏瑾天琴座 V2 Beta 1.0

我最近安装的这个版本针对 DeepSeek V4.1 Flash，提供字数、文风、剧情推进、总结等条目，也包含轻小说、西式文学等风格选项。它适合用来理解“同一个角色怎样受到不同写作规则影响”。

这些是可供选择的模块，不表示我全部开启，也不是越多越好。尤其当角色卡自带文风、总结或变量流程时，要避免叠加重复要求。预设里的思考提示与模型原生推理开关也不是一回事，适配关系应按具体版本说明核对。

这两套是我实际装过的例子，不是通用质量排名。换模型时，除了名称，还要检查消息角色、参数、工具调用和输出格式是否兼容。

06

类脑是什么，怎么找资源

类脑是围绕 AI、角色扮演和相关工具展开交流的中文社区，主要讨论与创作发布在 Discord 上。你可能见到“类脑 ΟΔΥΣΣΕΙΑ”和“类脑 ΙΛΙΑΣ”等服务器名称；浏览时以当前入口和频道说明为准。

酒馆提供应用，模型服务负责推理，类脑则提供创作者、作品和经验交流。社区里不只有角色卡，还有世界书、预设、插件、工具、教程，以及针对模型表现的讨论。它的价值在于能找到一套作品的完整上下文：作者想实现什么、依赖哪些组件、哪个版本有问题，以及后续如何修正。

我通常从类脑索引开始。它提供搜索、标签、书单和分类入口，可以先选角色卡、世界书、预设或插件，再按题材和玩法缩小范围。找到作品后回到 Discord 作者原帖，看发布说明、最新更新和置顶，而不是只凭排行榜下载。

读帖时重点看四件事：适配模型与版本、必备扩展、卡或预设的实际下载位置、当前已知问题。简介封面未必是可导入的角色卡，旧主楼也未必包含最新适配说明。初次加入需要按社区当前要求完成验证并获得相应频道权限，附件使用和转载则按作者说明处理。

社区的 MVU、变量、前端、数据库等标签很有参考价值，但标签不是完整依赖清单。它们可能对应一套脚本和状态协议，值得像看开源项目一样，先读说明、确认版本，再逐步接入。

07

从一个可观察的最小组合开始

第一次配置，可以先固定一个模型、一张简单文字卡和一套适配预设，开新对话跑通几轮，再加入世界书与记忆扩展。每次只改一类配置，比较人设、叙事、状态更新和响应时间，容易找到真正影响体验的变量。

排查时按链路看：接口有没有返回正文，最终提示词是否包含预期设定，历史是否被预算挤掉，世界书是否触发，工具和脚本是否配套，最后再看正则是否隐藏或改写了输出。这样比把所有异常都归因于“模型变笨了”更容易定位问题。

角色扮演的连贯性既依赖模型，也依赖应用持续提供什么信息、保存什么状态。酒馆把这些环节变得可见、可调，这也是它对熟悉 LLM 开发的人有意思的地方。
